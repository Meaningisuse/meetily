# 内部增强版更新策略

本仓库的内部增强版使用手动安装内部包的更新方式。当前没有已确认的独立更新源、签名公钥或内部版本发布规则，因此应用不应检查、下载或安装社区版更新。社区更新包可能覆盖本地增强能力。

## 用户操作

在“关于”页面的“更新说明”或系统托盘的“Internal Update Instructions”入口查看说明。请从内部发布负责人获取经过确认的内部安装包，再按内部发布说明手动安装。应用内的说明不提供社区下载链接，也不代表已经检查或确认最新内部版本。

界面展示通过本机应用接口读取的当前版本；读取期间显示“版本读取中”，读取失败后显示“版本未知”，不用硬编码版本作为已确认版本。读取失败时仍可打开更新说明，读取错误会如实提示；再次读取成功后显示本机返回的版本。更新策略不修改应用标识、现有版本号、会议数据库、设置或用户数据目录。

## 防护范围

- 启动时不安排联网检查更新的计时器。
- 默认检查、强制检查及系统托盘入口只返回或显示手动安装说明，不访问更新源；结果使用 `manual-install-required` 状态，不能解释为“已是最新版”。
- 直接调用更新服务的安装方法会拒绝，即使调用方持有旧的更新对象，也不能触发下载、安装、进度回调或重启。
- 更新对话框忽略旧的“发现更新”元数据，只显示内部包安装说明；通知入口不发布社区更新提示。
- Tauri 配置不保留社区更新源、公钥或 updater 权限，也不生成 updater 发布产物；原生应用不注册 updater 插件，从而封住绕过 React 服务直接调用插件的路径。

插件依赖和锁文件继续保留，避免把这次更新策略调整扩展成依赖清理。原生插件是否注册由启动构建代码决定，依赖存在不等于插件已对 WebView 开放。

## 验证与后续启用条件

行为回归位于 `frontend/tests/lib/internal-update-policy.test.tsx`，覆盖服务检查与安装拒绝、启动 hook、旧更新元数据、通知、关于页面、系统托盘及实际 Tauri 部署配置。原生注册调整应结合代码复核及原生构建/检查验证。测试和构建通过不等同于已完成安装包发布或真实用户升级验收。

未来启用应用内更新前，需要明确内部更新源、签名密钥管理、平台安装包、内部版本规则、发布及回滚流程，并设计可区分社区版与内部增强版的发布验证。应作为单独变更重新评审、测试和实际安装验收；不要只恢复一个界面开关、社区地址或原生权限。
